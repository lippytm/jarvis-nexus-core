## Slot 1 — Explain

Post ID: jarvis-media-20261029.substack.1

### Note copy

What would make an AI coding update useful to the next person who opens the project?

For Jarvis, I want that person to find three things together: the starting code version, the changed artifact and the results of checks that actually ran. A clear record gives a reviewer somewhere to begin and gives the next work session a specific stopping point.

Consider a conceptual example. A task asks for one correction to a draft-building tool. The return names its starting revision, links the proposed change, explains the behavior it should produce and records the checks performed. If a check could not run, the return says so and retains the unfinished task. It also names the next bounded action rather than implying the whole system is complete.

Review belongs to the exact content being considered. If that content changes, the earlier decision needs to be reconsidered for the new version. A checksum can help detect changed bytes; it does not establish who approved them or give an assistant permission to release anything.

This Note describes the engineering practice set out in Jarvis's Codex readiness and context guides. It is an explanation, not a new execution receipt. A retained change still needs its actual checks, review and any required owner release decision. It also does not establish a deployed service or connected publishing account.

## Slot 3 — Limits

Post ID: jarvis-media-20261029.substack.3

### Note copy

When a project update says “working,” what evidence should sit behind that word?

A saved artifact, a passing check and an available execution environment answer different questions. I want Jarvis updates to name the observation precisely enough that another person can understand its limits before choosing the next action.

Imagine a conceptual case in which a development commit passes tests on a GitHub runner, while a command in the intended local environment cannot start. The runner result is still useful evidence about the checks performed there. It does not demonstrate that the local environment has recovered. A catalog entry naming Codex, or a document describing a recovery workflow, supplies no actual command result from that environment.

The Codex readiness guide calls for a harmless command probe in the intended execution context. If it fails, retain the task, the failure context and the unfinished checkpoint. Avoid overlapping retries. A later actual successful command in that environment is needed before reporting recovery; even that success does not guarantee continuous availability.

The same care applies to collaboration. A matching digest checks content integrity. A proposed connection record describes intended scope. Neither alone establishes authenticated access, a running worker or an external delivery receipt. Those need their own observations and authorized controls.

This Note explains evidence boundaries from the Jarvis guides. It reports no new outage, recovery, reliability improvement or provider connection. An update can be useful while leaving an unknown clearly visible.

Which status in your next project update needs a more precise observation: saved, checked, available or delivered?

## Slot 4 — Bounded next step

Post ID: jarvis-media-20261029.substack.4

### Note copy

Before expanding an AI workflow, choose one unfinished task that another person could review in a single sitting.

Start with its current receipt. Name the project, mission, starting revision and intended destination. Check whether the task is already active or held before preparing more work. Retrieve only the context needed for its objective: a relevant decision, the source excerpt, a known failure and the acceptance check. Unrelated private conversations do not belong in a portable work bundle.

For a first exercise, use synthetic data and a draft-only action. A practical example is preparing a proposed correction to one file. Define the expected behavior before editing, keep the permitted tools and budget bounded, and retain any blocked execution state. Do not create a second task identity merely to get around a hold or a duplicate record.

Ask for a return that includes the actual artifact, the checks performed, unresolved limits and one next action. Keep a proposed memory update separate from an accepted project fact. If nothing could execute, the return should say what remains blocked and preserve the checkpoint rather than count the mission as completed.
