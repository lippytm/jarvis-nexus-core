## Slot 1 — Explain

Post ID: jarvis-media-20261029.linkedin.1

### Proposed caption

A useful AI engineering update should let another person inspect the work.

For a bounded Jarvis task, I want the handoff to answer three questions:

Which source revision did the task use?
What changed in the resulting artifact?
Which checks actually ran against that result?

Review belongs to that exact version. If the content changes, the earlier review needs to be reconsidered.

This gives a collaborator a concrete starting point for evaluation. It does not establish that the software is deployed or that a service is available.

Before the next handoff, choose one small outcome and agree on the evidence needed to review it.

What information do you look for first when you review work prepared with an AI assistant?

| 3 — Evidence | Review applies to exact content. An edit needs a fresh review decision. | A review of one version cannot be assumed to approve later changes. |
| 4 — Next step | Agree on one outcome and its acceptance check before starting. | Select a small task and decide what evidence would let a reviewer assess it. |

## Slot 2 — Demonstrate

Post ID: jarvis-media-20261029.linkedin.2

### Proposed caption

Here is a small review exercise for an AI-assisted workflow.

Suppose a draft has been reviewed. The assistant then changes one sentence in its checkpoint note.

Should the old review still cover the updated record?

For the Jarvis context workflow, every content change invalidates the saved context review. A checkpoint edit counts as a change, even if the main task description is identical.

A meaningful check would save and review a synthetic record, edit that note, then confirm the updated record requires review again. It should also confirm the edited text survives reopening the ledger.

That exercise is a proposed demonstration here, not a report of a new run.

The practical next step is to inspect the implementation and run the check against a named revision before presenting its result.

Where does your workflow make changed content visible to its reviewer?

### Four-slide script and plain-text equivalent

| Slide | Proposed on-slide text | Plain-text equivalent |
|---|---|---|
| 1 — Problem | A reviewed draft changes. Does its old review still apply? | Consider a synthetic record whose checkpoint note changes after review. |
| 2 — Method | Save → review → edit checkpoint → reopen. Proposed exercise. | Use isolated synthetic data to save a record, review it, change its checkpoint note and reopen its ledger. This exercise has not been run for this post. |
| 3 — Evidence | Expected: edited text retained; earlier review invalidated. No new result claimed. | The expected behavior is retention of the edit and a requirement for a fresh review. An actual run and receipt are still needed. |
| 4 — Next step | Run at an exact revision; retain the actual result. | Inspect the implementation, execute a meaningful check against a named version and retain its observed result before claiming success. |

## Slot 3 — Limits

Post ID: jarvis-media-20261029.linkedin.3

### Proposed caption

A passing development check answers a bounded question.

It can show that a named behavior passed in the environment where the check ran. It does not tell us whether a separate assistant runtime is available, whether a platform account is connected, or whether someone approved a release.

The Jarvis readiness contract keeps those observations separate: attempt a harmless command in the intended execution context, retain the result, and report runner checks as runner evidence.

When a runtime is unavailable, preserve the unfinished task and its checkpoint. Do not describe a successful CI run as proof that the blocked environment recovered.

For the next project update, name the artifact, the check environment and the remaining evidence gap.

Which availability claim in your project would benefit from its own direct check?

### Four-slide script and plain-text equivalent

| Slide | Proposed on-slide text | Plain-text equivalent |
|---|---|---|
| 1 — Problem | Passing CI does not establish every runtime's availability. | A check on one runner cannot establish that another execution environment is usable. |
| 2 — Method | Probe the intended environment. Record runner checks separately. | Attempt a harmless command where the work is intended to run and keep that observation distinct from CI evidence. |
| 3 — Evidence | Name what ran, where it ran and what remains unverified. | Report the actual check, its environment and its practical limits without inventing connectivity or release authority. |
| 4 — Next step | If blocked, retain the task and checkpoint. Reconcile before retry. | Preserve unfinished work and its last evidence. Do not create duplicate work or infer recovery without a later successful actual command. |

Visual specification: use independent rows for “Intended execution context,”
“CI runner,” “Account access,” and “Owner release.” Avoid green online dots,
uptime graphs or automatic arrows between rows. Proposed visual description:
“Four slides distinguish a CI runner from the intended execution context and
keep account access and release authority separate. Blocked work retains a
checkpoint rather than acquiring a success label.”

Source: [Codex readiness contract](../CODEX_JARVIS_READINESS.md), “Operational
preflight” and “Available fallback, not an always-on service.” This copy makes
no claim about today's connection status or measured reliability.

## Slot 4 — Bounded next step

Post ID: jarvis-media-20261029.linkedin.4

### Proposed caption

Before expanding an AI workflow, make one handoff reviewable.

Choose one unfinished task. Name the source revision, the permitted actions and the destination. Retrieve only the context needed for that task.

Ask the preparing assistant to return the changed artifact, actual checks, unresolved limits and a checkpoint for continuation. Keep a proposed result separate from an accepted project fact.

Then review that exact revision before deciding what to release.

This is the working pattern I want Jarvis to support across the portfolio: a scoped task with a record another person can assess and resume.

For a first exercise, use synthetic data and a draft-only action. Leave publication, purchases and account changes outside that exercise.

What is one unfinished task small enough to make reviewable today?

### Four-slide script and plain-text equivalent

| Slide | Proposed on-slide text | Plain-text equivalent |
|---|---|---|
| 1 — Problem | An unfinished task needs a reviewable next action. | Select one existing unfinished task rather than creating overlapping work. |
| 2 — Method | Scope the task, source, destination and permitted actions. | Identify the task's starting revision, intended destination and allowed actions, and retrieve only necessary context. |
| 3 — Evidence | Return the artifact, actual checks, limits and checkpoint. | Retain concrete output and observed checks, label unresolved work, and provide a continuation checkpoint. A proposal is not an accepted fact. |
| 4 — Next step | Start with synthetic data and a draft-only action. | Use a bounded exercise and review its exact revision. Public actions, spending and account changes require their own authority. |
