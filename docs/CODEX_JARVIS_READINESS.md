# Codex in AI Building AI

Codex is a named engineering-assistant target, distinct from ChatGPT, the OpenAI API and GitHub. The existing catalog, portable draft/return contract, inactive assistant factory, connection report and browser composer accept the exact ID `codex`.

## Responsibility

The intended Jarvis role is bounded coding, debugging, diagnostics, tests, reviewed tool proposals and evidence. Hermes routes the mission; Fabric supplies scoped tools; MemPalace retains project/evidence references; an evaluator reviews results; the owner controls release, public actions and spending. Those architecture labels do not establish a deployed runtime.

## What works in this source

The composer exports a Codex-targeted draft. The existing SQLite ledger stages it, requires exact-content review before export, binds an imported return to the original target and digest, preserves the state across reopen and detects duplicates. The factory creates inactive role specifications; it does not start Codex.

Regression fixtures are local synthetic records, not authenticated Codex messages. Read observations are integrity-checked metadata, not runtime availability or permission grants. There is no live Codex dispatcher, automatic restart controller, failover worker or authentication service in this change.

## Operational preflight

Before a real coding task, the operator or orchestrator must:
1. Read the latest mission, source revision and unfinished-work receipt.
2. Confirm authorized access to the exact repository and development branch.
3. Attempt a harmless command in the actual intended execution environment. Retain success/failure and the execution context; never infer availability from a catalog entry or global status page.
4. Confirm dependencies and run meaningful source/behavior checks before claiming success.
5. Save the exact output/commit, test evidence, unresolved errors and next task.

If the execution attempt fails, record `execution_blocked`, preserve the task and partial output, and avoid overlapping retries. A later successful command is required before calling that environment recovered. The current ChatGPT session supplies no server restart/reconnect control.

## Available fallback, not an always-on service

When local execution is unavailable, authorized GitHub read tools can inspect code. Development commits may proceed within the owner's scope and approval checks, using a refreshed branch and expected-head guard. GitHub Actions can then supply actual syntax and behavior evidence. Link the specific commit and CI run. A passing GitHub runner is not a passing Codex runtime probe.

If repository access or approval is unavailable too, keep an exact private candidate and a clear blocker. Do not repeatedly overwrite work, bypass approval, invent successful checks or claim guaranteed uptime. Timed work is separate from a continuously running Codex session.

## Boundaries and use

Codex has the same review and external-action boundaries as other Jarvis roles. No merge, production deployment, purchase, financing, live trading or public posting is authorized by adding this target. Trading Bots stays R&D; RoboParty stays deferred. Existing sixteen targets remain supported.

Open `web/jarvis-composer.html` locally and select “Codex engineering.” Existing `scripts/jarvis_network.py factory` accepts `--targets codex,github` with an actual source-context revision and fresh output filename. Export remains a manual handoff.

Official quickstart: https://learn.chatgpt.com/docs/quickstart . Product/account access and environment configuration must be verified separately. This source does not provision a paid API sandbox or change subscriptions.

Run the existing verifier and Node suite to validate this development change:
```bash
python scripts/verify_control_tower.py
node --test --test-reporter=tap tests/*.mjs
```

Actual CI results belong in the work receipt for the published commit. Browser rendering, live Codex execution, automatic recovery and live-provider handoffs require separate evidence.
